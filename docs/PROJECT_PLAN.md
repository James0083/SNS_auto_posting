# SNS 자동 포스팅 — 통합 프로젝트 계획서 (v1)

> **이 문서는 무엇인가**: `SNS_auto_posting` 저장소(README: "인스타그램, 네이버블로그, 스레드 등의 SNS에 포스팅을 자동화")를 실제로 구현하기 위한 **마스터 계획서**입니다.
> 서로 다른 시점에 작성된 3개의 원본 문서를 하나의 아키텍처로 통합하고, 문서 간 충돌 지점을 해소하고, 빠진 부분을 채웠습니다.
>
> **이 문서 하나만으로는 부족합니다.** 네이버 블로그 트랙은 셀렉터·함정 목록 등 방대한 실측 정보를 담은 원본 문서를 그대로 참조해야 하므로, 아래 3개 원본을 `docs/reference/`에 그대로 보존해두었습니다.
>
> | 원본 문서 | 저장 위치 | 이 계획서에서의 역할 |
> |---|---|---|
> | 네이버 블로그 빌드 프롬프트 (개정 3판) | [`docs/reference/naver-blog-build-prompt.md`](./reference/naver-blog-build-prompt.md) | 네이버 블로그 트랙의 **1차 소스**. 이 계획서는 이걸 요약·참조만 하고 내용을 복제하지 않습니다. |
> | 릴스 각색 규칙 (`CLAUDE.md`) | [`docs/reference/reels-adaptation-rules.md`](./reference/reels-adaptation-rules.md) | 릴스 각색 트랙의 **콘텐츠 품질 규칙**. 그대로 앱의 시스템 프롬프트로 임베딩됩니다. |
> | 릴스 자동화 웹페이지 계획서 (v1) | [`docs/reference/reels-webapp-plan-v1.md`](./reference/reels-webapp-plan-v1.md) | 초기 아이디어 문서. 이 계획서가 **대체**합니다(아키텍처를 기존 스택으로 통합하면서 일부 제안을 기각 — 4장 참고). |
>
> **개정 이력**
> - v1 (이 문서): 네이버 블로그 원본 스펙 + 인스타그램 게시물(사진) 확장 검토 + 릴스 각색 CLAUDE.md/계획서, 3개 소스를 하나의 저장소·하나의 스택으로 통합.

## 0. 왜 이 통합이 필요한가

세 원본 문서는 각각 **다른 가정**으로 쓰였습니다.

- 네이버 블로그 문서: Next.js + SQLite + Playwright 모놀리스, 브라우저 자동화로 실제 발행까지 수행.
- 릴스 각색 계획서(v1): "React SPA + 서버리스 함수"라는 **별도 스택**을 제안, 발행 자동화는 처음부터 범위 밖(사용자가 직접 복사해서 올림).
- CLAUDE.md: 스택과 무관하게 **콘텐츠 품질 규칙**만 정의(어떤 앱이 이걸 구현하든 적용 가능).

이 셋을 그대로 각각 구현하면 저장소 하나에 앱이 사실상 3개 생깁니다. 이 문서는 **하나의 앱, 하나의 스택, "채널×유형" 매트릭스로 확장 가능한 구조**로 합치는 것이 목표입니다.

## 1. 프로젝트 목표 및 범위

| 항목 | 내용 |
|---|---|
| 목적 | 키워드 기반 자동 발굴이든, 사용자가 준 소재든, 해외 콘텐츠 번역이든 — 입력 방식과 무관하게 **SNS별 규격에 맞는 완성 콘텐츠**를 생성 |
| 사용자 | 개발을 모르는 1인 운영자(네이버 블로그 트랙 기준) / 콘텐츠 제작자 본인(릴스 각색 트랙 기준) — **두 트랙의 사용자 숙련도가 다를 수 있음**, UI는 항상 비개발자 기준으로 설계 |
| 결과물 형식 | 채널별로 다름 — 네이버는 **실제 발행**까지, 인스타그램(게시물·릴스)은 **로컬 생성 + 다운로드**까지 |

### 1-1. 이번 버전에서 확정한 범위 경계

앞선 검토에서 사용자가 명시적으로 결정한 사항을 그대로 절대 조건으로 승격합니다.

1. **인스타그램(게시물·릴스) 자동 업로드는 이번 범위에서 제외**한다. Graph API 연동은 로드맵상 다음 단계(13장)로 미룬다. 이번 버전은 "로컬에서 콘텐츠를 만들고 다운로드"까지가 완료 기준이다.
2. **인스타그램 게시물은 캐러셀을 옵션(토글)으로 지원**한다. 토글이 꺼지면 1장, 켜지면 N장(슬라이드).
3. **릴스는 이번 범위에서 스크립트(본문·제목)와 정지 이미지까지만** 다룬다. 실제 동영상 생성·편집은 범위 밖(13장 로드맵).

## 2. 절대 조건 (전체 트랙 공통)

원본 네이버 문서 2장의 원칙 중 채널과 무관하게 적용되는 것들을 전체 공통 원칙으로 승격합니다.

### 2-1. AI 호출은 반드시 `claude -p` CLI로 (원본 2-1 그대로 승계)

세 트랙 모두 동일합니다. `@anthropic-ai/sdk` 금지, stdin 전달, 비전 호출도 `@경로` 첨부 방식 동일. **릴스 각색 트랙은 이미지 여러 장을 한 번에 첨부하는 경우가 네이버보다 잦으므로**(원문 캡처 이미지 + 참고 이미지), `opts.images` 배열의 개수 상한을 실측해 문서화해야 함 — [9장 함정 후보](#9-예상-함정-목록-미검증--실측-필요) 참고.

### 2-2. 완전 로컬 — 단, 트랙별로 "완전"의 의미가 다름

- 네이버 블로그: 원본 그대로, DB·세션·이미지·스크린샷 전부 로컬.
- 인스타그램 게시물·릴스: **업로드 자동화가 없으므로 애초에 로컬 원칙과 충돌할 지점이 없음**(이전 검토에서 우려했던 "Graph API용 공개 URL 필요" 문제는 범위 제외로 해소됨). 결과물은 `data/instagram/`, `data/reels/`에 저장하고 사용자가 다운로드.

### 2-3. 이미지에는 텍스트를 넣지 않는다 (CLAUDE.md 16~17장 → 전체 트랙 공통 원칙으로 승격)

원래 릴스 각색 문서에만 있던 규칙이지만, **인스타그램 게시물 트랙에도 그대로 적용하는 것을 권장**합니다(피드 이미지에 텍스트 오버레이가 있으면 캡션과 중복되거나 깨져 보일 위험, 저작권 표시가 실수로 재현될 위험도 줄어듦). 이미지 생성 프롬프트 끝에 `no text, no letters, no words, no watermark, no logo`를 강제하는 것을 전체 이미지 생성 파이프라인(네이버 크롤링용 제외 — 크롤링은 기존 사진이므로 해당 없음)의 공통 규칙으로 둡니다.

### 2-4. 작업 간 독립성 (CLAUDE.md 1장 → 릴스 각색 트랙 전용 원칙)

> "새로운 원문이 제공될 때마다 이전에 작업한 내용과 절대 연결짓지 않는다."

이건 UI 매너의 문제가 아니라 **코드 설계 제약**입니다. `runClaude`/`runClaudeJson` 호출 시 이전 job의 결과물(제목, 톤, 소재)을 프롬프트에 절대 섞지 마세요. 릴스 각색 파이프라인은 매 job마다 시스템 프롬프트(CLAUDE.md 전체) + 이번 원문만 담아 완전히 새로 호출해야 하며, "이전 대화 맥락" 같은 상태를 유지하는 구조(예: 같은 대화 세션을 이어 쓰는 방식)를 쓰면 안 됩니다.

### 2-5. 네이버 전용 원칙 (Playwright, 로그인 자동화 금지, 발행 안전장치) — 그대로 유지

원본 2-2 후반부·2-3·2-4·2-5는 네이버 블로그 트랙에만 해당합니다. 인스타그램 두 트랙은 브라우저 자동화 자체가 없으므로 해당 없음.

## 3. 기술 스택 (통일 — 릴스 계획서 v1의 제안을 기각)

```
Next.js 15 (App Router) + React 19 + TypeScript strict
better-sqlite3   — 로컬 DB (전체 트랙 공통)
playwright       — 브라우저 자동화 (네이버 트랙 전용)
zod              — AI 응답 구조 검증 (전체 트랙 공통)
sharp            — 이미지 리사이즈/크롭/포맷 변환 (인스타그램 두 트랙 신규)
archiver(or 동급) — 결과물 zip 다운로드 (인스타그램 두 트랙 신규)
```

**왜 릴스 계획서 v1의 "React SPA + 서버리스 함수" 제안을 채택하지 않는가**: 저장소 하나에 스택이 두 개면 배포·설정·의존성 관리가 이중화됩니다. 네이버 트랙이 이미 Next.js API 라우트 + SQLite로 "로컬 대시보드"라는 동일한 제품 형태(로컬에서 `npm run dev`로 띄우는 개인용 도구)를 요구하므로, 릴스·인스타그램 트랙도 **같은 앱의 새 화면/새 API 라우트**로 얹는 것이 자연스럽습니다. 사용자가 서버리스 배포를 원한다면 그건 이후 별도 결정 사항으로 남겨둡니다.

개발 포트·`tsconfig` paths·검증 스크립트 실행 방법(`tsx` 또는 loader hook)은 원본 문서 3장 그대로 승계합니다.

## 4. 채널×유형 매트릭스

| 채널 | 유형 | 입력 | 결과물 | 발행 |
|---|---|---|---|---|
| 네이버 블로그 | 자동발굴 / 체험단 / 브랜딩 | 키워드 또는 주제+내용 | 섹션 배열 → 에디터 타이핑 | **실제 발행** (원본 문서 그대로) |
| 인스타그램 게시물 | 자동발굴 / 체험단 / 브랜딩 (네이버와 유형 공유) | 동일 | 캡션+해시태그+이미지 1~N장 | **로컬 다운로드까지** |
| 인스타그램 릴스 | 해외 콘텐츠 번역·각색 (신규 유형) | 원본 이미지/텍스트 (해외 SNS 콘텐츠) | 후킹 제목 3안+본문+재생성 이미지 1~N장 | **로컬 다운로드까지** |

이 매트릭스가 이번 통합의 핵심입니다. "자동발굴/체험단/브랜딩"은 네이버 전용이 아니라 **채널과 독립적인 콘텐츠 생성 방식**으로 재정의하고, 인스타그램 게시물 트랙도 그대로 재사용합니다. 반면 "해외 콘텐츠 번역·각색"은 완전히 새로운 입력 방식(사용자가 해외 원문을 준다)이라 별도 유형으로 추가합니다.

### 4-1. 네이버 블로그 — 상세 스펙은 원본 문서를 그대로 따름

이 계획서에서 반복하지 않습니다. `docs/reference/naver-blog-build-prompt.md` 3~13장을 그대로 구현하세요. 아래 두 트랙 개발 중에도 **원본 문서의 8장(작업 원칙)·9장(진행 순서)·10장(검증 체크리스트) 형식은 그대로 재사용**합니다(11~12장 참고).

### 4-2. 인스타그램 게시물 (사진) — 신규 확장

- 사진 소스 선택(내 사진/크롤링/AI생성/없음)은 네이버 파이프라인의 `localPhotos.ts`/`images.ts`/`imagegen.ts`를 그대로 재사용.
- **캐러셀 토글**: `carouselEnabled`(기본 false) + `carouselCount`(2~10, 토글 켰을 때만 노출). 꺼짐 → 이미지 1장, 켜짐 → N장을 "슬라이드"로 생성하며 각 슬라이드에 역할(`cover`/`body`/`cta`)을 부여해 프롬프트에 반영.
- 캡션+해시태그 생성은 네이버 본문 생성과 별도 프롬프트(7-3 참고). 마크다운 무력화 로직(원본 7-8)은 불필요 — 인스타그램은 자동변환 에디터가 아니므로 AI에게 "쓰지 마라"고 지시하는 것으로 충분.
- 이미지 비율은 정사각형(1:1) 또는 4:5로 강제(2-3의 텍스트 미포함 원칙과 함께).

### 4-3. 인스타그램 릴스 — 해외 콘텐츠 번역·각색 (신규 유형)

CLAUDE.md(`docs/reference/reels-adaptation-rules.md`) 1~19장을 코드로 옮긴 것이 이 트랙의 전부입니다. 7-3에서 모듈 단위로 분해합니다.

## 5. 데이터 모델 (통합 스키마)

```sql
-- 네이버 블로그 (원본 문서 5장 그대로)
settings / jobs / sources / ideas / drafts / images / posts / job_logs

-- 인스타그램 게시물 (신규)
ig_posts  (id, job_id, draft_id, caption, hashtags_json,
           carousel, slide_count, created_at)
ig_images (id, ig_post_id, slide_index, role, local_path,
           source_site, verdict_ok, verdict_reason, created_at)

-- 인스타그램 릴스 — 해외 콘텐츠 번역·각색 (신규)
reels_jobs   (id, status, input_type,        -- input_type: 'text'|'image'|'both'
              source_text, source_image_paths_json,
              created_at, updated_at)
reels_titles (id, reels_job_id, candidate_index, text, chosen, created_at)
reels_drafts (id, reels_job_id, title_id, body_text, cta_included_json,
              qc_json,                        -- 19장 체크리스트 자동검증 결과
              created_at)
reels_images (id, reels_job_id, slide_index, local_path,
              gen_prompt, verdict_ok, verdict_reason, created_at)
```

- `reels_jobs.source_image_paths_json`: 업로드된 원본 캡처 이미지 여러 장의 로컬 경로 배열. 원본은 절대 그대로 사용하지 않고(CLAUDE.md 16장) 비전 분석의 입력으로만 씀.
- `reels_drafts.qc_json`: 자동으로 검증 가능한 체크리스트 항목만 기계적으로 채움(7-3-5 참고). 톤·후킹 강도처럼 주관적인 항목은 사람이 확인해야 하므로 QC에 넣지 않음 — **"검증했다고 거짓으로 표시하지 마라"**는 원본 문서 8-2 원칙을 여기서도 지킵니다.
- 네이버의 `posts`(발행 결과) 테이블과 `ig_posts`/`reels_jobs`를 분리한 이유: `blog_url`, `screenshot`, `published_at` 같은 발행 전용 컬럼이 인스타그램 두 트랙에는 항상 NULL이 되어 스키마가 지저분해짐.
- `PRAGMA journal_mode = WAL`, `globalThis` 커넥션 캐싱 등 원본 5장의 SQLite 운용 원칙은 전체 트랙 공통 적용.

## 6. 파일 구조 (통합)

```
config.ts
lib/
  claude.ts                  (공통 — 원본 6-1)
  db.ts / settings.ts / paths.ts / log.ts   (공통)
  playwright.ts               (네이버 전용 — 원본 6-2)

- 이건 이번 통합 과정에서 발견한 **미검증 가설**입니다. 실제로 사용자가 지금까지 이 규칙으로 수동 작업하면서 별표를 일부러 남겨뒀을 수도 있고(캐주얼한 스타일 요소로), 매번 손으로 유니코드 볼드체(예: 𝗶𝗻𝘀𝘁𝗮𝗴𝗿𝗮𝗺 굵게 폰트)로 바꿔왔을 수도 있습니다. **구현 전에 사용자에게 직접 확인**하세요 — "지금까지 결과물의 `**단어**`를 인스타그램에 그대로 붙여넣었을 때 실제로 굵게 보였는지"를 원본 문서 8-1(추측 금지, 증거로 확인) 원칙대로 물어보고 답에 따라:
  - 그대로 별표가 보였다면 → `boldConvert.ts`가 마크다운 `**text**`를 유니코드 수학 알파벳 기호 볼드체로 치환하는 후처리를 추가해야 진짜 "굵게"가 됩니다.
  - 이미 다른 방식으로 처리하고 있었다면 → 그 방식을 그대로 코드화합니다.
- 이 항목은 9장 예상 함정 목록에도 최상단으로 올려둡니다.

**`lib/ai/reelsQC.ts`** (CLAUDE.md 19장 체크리스트)

19개 체크리스트 항목 중 **기계적으로 검증 가능한 것만** 자동화하고 나머지는 사람 확인용으로 남깁니다.

| 체크리스트 항목 | 자동 검증 가능? | 방법 |
|---|---|---|
| 해시태그가 들어가지 않았는가 | ✅ | 정규식으로 `#` 패턴 탐지 |
| 코드 블록 형태로 제공됐는가 | ✅ | 파이프라인 출력 형식으로 보장(애초에 그렇게 조립) |
| 굵게 강조가 있는가 | ✅ | `**...**` 또는 변환된 유니코드 볼드 패턴 존재 여부 |
| CTA가 격식체(반말 없음)인가 | ⚠️ 부분적 | 흔한 반말 종결어미(`~해`, `~하자`) 패턴 매칭으로 1차 스크리닝만, 최종 판단은 사람 |
| 첫 문장이 충분히 후킹되는가 / 문체 톤 / 과학적 정확성 | ❌ | 사람이 확인. QC 결과에 "미검증 — 사람 확인 필요"로 명시 |
| 안전 경고 포함 여부 (위험 소재일 때) | ❌ | 콘텐츠 성격 판단이 필요해 자동화 어려움. 화면에 "위험 소재 감지 시 경고 문구 확인" 체크박스로 사람에게 상기 |

`qc_json`에는 자동 검증 결과만 저장하고, 화면에는 나머지 항목을 **사람이 직접 체크하는 체크박스**로 그대로 노출합니다(원본 문서 8-2 "직접 확인하지 않은 것을 됨이라고 쓰지 마라" 원칙 계승).

## 9. 예상 함정 목록 (미검증 — 실측 필요)

## 11. 진행 순서 (통합 개발 단계)

   개발 순서상 인스타그램 두 트랙을 먼저 끝내 "완성 콘텐츠 생성"이 되는지
   전체 파이프라인을 조기에 검증하는 것도 좋은 전략입니다.

A. 인스타그램 게시물 — igCaption.ts + 캐러셀 토글 + 이미지 비율 강제
B. 릴스 각색 — reelsHook.ts + reelsBody.ts (CLAUDE.md 시스템 프롬프트 통짜 삽입)
C. 릴스 각색 — reelsImage.ts (9-2 비전 첨부 개수 실측 먼저)
D. 유니코드 볼드 변환 여부 확정(사용자 확인 후 boldConvert.ts 구현 또는 스킵) + reelsQC.ts

4~9. 네이버 트랙 — 원본 문서 9장 그대로 (수집→글쓰기→이미지→에디터 자동화→UI)
```

## 12. 검증 체크리스트 (통합)

- 네이버 블로그: 원본 문서 10장 A/B 구분 그대로.
- 인스타그램 게시물 (신규):
  - [ ] 캐러셀 토글이 꺼지면 이미지 1장, 켜지면 설정한 장수만큼 생성된다
  - [ ] 캡션 첫 1~2줄만으로 내용이 파악된다
  - [ ] 해시태그 개수가 설정 상한을 넘지 않는다
  - [ ] 이미지 비율이 1:1 또는 4:5로 고정 생성된다
  - [ ] 다운로드한 zip에 이미지+캡션 텍스트가 모두 포함된다
- 인스타그램 릴스 (신규):
  - [ ] 후킹 제목 3안이 서로 다른 접근(반전/숫자/질문 등)으로 나온다
  - [ ] 본문에 해시태그가 전혀 없다
  - [ ] **굵게 표시가 실제 인스타그램 캡션에서 굵게 보인다** (9장 함정 1번 — 유니코드 변환 적용 시)
  - [ ] 원본 이미지의 실존 인물·브랜드 로고·워터마크가 결과 이미지에 재현되지 않는다
  - [ ] 이미지에 텍스트/오버레이가 없다
  - [ ] 이미지/제목/본문을 개별적으로 재생성할 수 있다(전체 재실행 불필요)
  - [ ] 이전 job의 소재·톤이 다음 job에 섞이지 않는다(2-4 검증 — 연속으로 다른 주제 2건을 돌려 결과가 서로 무관한지 확인)
  - [ ] `reelsQC.ts`의 자동 검증 항목과 사람 확인 체크박스가 화면에 분리 표시된다

## 13. 리스크 및 향후 로드맵

### 13-1. 리스크 (릴스 계획서 v1 9장 + 원본 문서 12장 통합)

- 이미지 생성 API 자체의 저작권 정책(실존 인물 생성 제한 여부 등)은 API 제공자 정책도 별도 확인 필요.
- 문체 일관성(~습니다체/~죠/~나요 비율)은 자동 QC로 완전히 보장되지 않으므로 초기엔 사람 검수 비중을 높게 유지.
- 민감 콘텐츠(의학·사망·극단적 다이어트 등) 필터가 과도하게 순화하거나 반대로 놓치는 사례는 별도 회귀 테스트 케이스로 축적.
- API 호출 비용(이미지 생성 + LLM) — 개별 재생성이 자유로운 구조라 남용 시 비용이 늘 수 있음. `imageCandidates`/`cfImageSteps`와 별개로 릴스·게시물 트랙에도 하루 생성 편수 정도의 소프트 리밋을 옵션으로 고려.
- 검색으로 가져온 이미지·해외 원본 콘텐츠는 저작권 분쟁 소지가 있으므로(원본 문서 12장과 동일 원칙), 재생성 이미지가 원본과 "컨셉만 유사"한지 "그대로 복제"한 것인지의 경계는 최종적으로 사람이 판단해야 함을 UI에 안내.

### 13-2. 로드맵 (이번 범위에서 명시적으로 제외한 것들)

| 항목 | 현재 상태 | 다음 단계 |
|---|---|---|
| 인스타그램 Graph API 자동 업로드 | 제외 | 비즈니스 계정 전환 + Meta 앱 심사 절차부터 별도 검토 |
| 릴스 실제 동영상 생성/편집 | 제외 | 이미지 슬라이드쇼 변환(ffmpeg) 또는 외부 영상 생성 API 검토 |
| 스레드(Threads) 지원 | 제외 (README에 언급만 있음) | 인스타그램 게시물 트랙과 유사한 구조로 채널 매트릭스에 추가 가능 — 캡션 길이·톤 규칙만 다시 정의하면 됨 |
