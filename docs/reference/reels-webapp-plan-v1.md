# 릴스 콘텐츠 각색 자동화 웹페이지 — 프로젝트 계획서

## 0. 문서 개요

본 문서는 해외 SNS(Instagram Reels/Shorts) 원본 콘텐츠를 입력하면, ① 저작권에 저촉되지 않는 새 이미지 생성, ② 후킹 제목 추천, ③ 한국어 릴스 본문 번역·각색을 자동으로 수행하는 웹페이지 구축을 위한 기획서다.

기능 요구사항과 결과물 품질 기준은 프로젝트의 `CLAUDE.md`에 정의된 규칙을 그대로 따른다. 본 문서는 그 규칙을 실제 서비스 기능/화면/로직으로 옮기기 위한 설계 문서이며, 개발자(또는 Claude Code)가 이 문서만 보고 구현에 착수할 수 있도록 작성한다.

## 1. 프로젝트 목표

| 항목 | 내용 |
|---|---|
| 목적 | 원본 캡처 이미지·본문을 넣으면, 저작권 안전한 새 이미지 + 후킹 제목 + 한국어 릴스 본문을 자동 생성 |
| 사용자 | 콘텐츠를 제작·번역하는 1인 운영자 (본인) |
| 핵심 가치 | 반복 작업(이미지 재생성, 문체 규칙 준수, CTA 구성) 자동화로 제작 시간 단축 |
| 결과물 형식 | 이미지 파일(다운로드) + 제목 텍스트(복사) + 본문 텍스트(코드 블록, 복사) |

## 2. 핵심 기능 3가지

### 기능 A. 이미지 재생성 (저작권 회피)

- **입력**: 원본 캡처 이미지 파일 (1장 이상, 여러 장 업로드 가능)
- **처리**:
  1. 업로드된 이미지를 비전 모델로 분석해 핵심 컨셉(피사체, 구도, 색감, 분위기)을 추출
  2. 저작권·초상권에 저촉되는 요소를 식별하고 배제 목록에 추가 (실존 인물 얼굴, 브랜드 로고, 영화/드라마 스틸컷, 캐릭터, 워터마크, 계정명 등)
  3. 배제 목록을 제외한 핵심 컨셉만으로 이미지 생성 프롬프트를 구성 (`CLAUDE.md` 17.1, 17.4 기준)
  4. 텍스트/워터마크/캡션이 이미지 안에 들어가지 않도록 프롬프트에 `no text`, `no overlay`, `no watermark`, `no logo` 등 명시 (17.2 기준)
  5. 세로형 4:5 또는 9:16 비율로 생성 (17.1 기준)
  6. 콘텐츠 성격(과학/의학/여행/사회이슈 등)을 자동 분류해 17.5의 톤 가이드를 프롬프트에 반영
- **출력**: 원본과 유사한 컨셉이지만 완전히 새로 생성된 이미지 1~N장, 다운로드 가능
- **예외 처리**: 이미지 생성 API 연동이 안 된 상태라면 "이미지 생성이 현재 불가능합니다" 안내와 함께 제목/본문 기능은 정상 동작

### 기능 B. 후킹 제목 추천

- **입력**: 원본 제목/캡션 텍스트, 또는 원본 이미지(텍스트가 없을 경우 이미지 시각 정보로 대체)
- **처리** (`CLAUDE.md` 4장 기준):
  1. 원문 제목을 직역하지 않고 완전히 재구성
  2. 우선순위: ① 반전 ② 놀라운 숫자 ③ 질문 ④ 일상 대비 ⑤ 예상 밖 현상
  3. 2줄 이내로 간결하게 구성 (이미지 오버레이용 규격 참고, 단 이미지엔 삽입하지 않음 — 16장)
- **출력**: 후킹 제목 3개 정도를 후보로 제시하고 사용자가 선택 또는 재생성 요청 가능

### 기능 C. 본문 번역/각색

- **입력**: 
  - 필수: 원본 이미지 또는 원본 텍스트 중 최소 1개
  - 선택: 원본 캡션/본문 텍스트 (있으면 이를 우선 참고, 없으면 이미지 시각 정보 기반으로 각색 — 14장 기준)
- **처리**: `CLAUDE.md` 1~13장, 15장 규칙을 그대로 반영한 번역 파이프라인 (아래 4장 참고)
- **출력**: 코드 블록 형태의 완성된 릴스 본문 (15장 기준), 바로 복사 가능

```

     ↓

     ├─ (B) 제목 추천 파이프라인 실행

     ↓

     ↓
[7] 완료 → 다음 원본 콘텐츠 입력 시 이전 세션과 완전히 독립적으로 처리 (1장 기준)
```

## 4. 본문 각색 로직 상세 설계

본문 생성 파이프라인은 `CLAUDE.md` 규칙을 아래와 같이 단계별 체크로 구현한다.

### 4-1. 입력 판단
| 입력 상태 | 처리 방식 |
|---|---|
| 텍스트 있음 | 텍스트를 주 소스로 번역·각색, 이미지는 보조 참고 |
| 텍스트 없음, 이미지만 있음 | 이미지 시각 정보(피사체, 오버레이 텍스트, 등장 캐릭터 등)를 주 소스로 구성 (14장) |
| 텍스트 부실(한두 줄) | 텍스트 + 이미지 정보를 함께 반영, 이미지 비중을 높임 |

### 4-2. 번역·각색 규칙 (1장)
- 직역 금지, 한국어 SNS 문장으로 재구성
- 원문의 비유·은유는 살려서 번역
- 숫자·단위·고유명사·의학용어는 임의 변경 금지, 필요 시 괄호 병기 (대중화된 용어는 생략)
- 장황하거나 반복되는 원문은 핵심 대비 구조로 압축 (13장)

### 4-3. 구조화 (2장, 12장)
- 후킹 → 개념 설명 → 원리/과정 → 수치/비교 → 의미 → 마무리 → CTA 순서 기본값
- 항목 나열형 콘텐츠는 5가지 스타일(개별 이모지형/순번형/3단구조/대비형/소제목+불릿형) 중 콘텐츠 성격에 맞게 자동 선택

### 4-4. 문체 규칙 (3장)
- 평서문: ~습니다체 중심, ~죠/~나요/~데요는 문단당 1~2회로 제한
- 질문형 문장: ~까요/~나요
- CTA: 항상 격식체, 예외 없음

### 4-5. 안전/윤리 필터 (6, 7, 9, 11장)
| 케이스 | 처리 |
|---|---|
| 의학/생명과학 콘텐츠 | 과장 금지, 조건부 표현 유지, 담담한 톤 |
| 위험 장치·화재·전기 등 | 안전 경고 유지, 실행 지침화 금지 |
| 원문에 광고/특정 계정 팔로우 유도 | 제거 |
| 원문에 종교·이념적 프레이밍 | 제거, 객관적 사실만 추출 |
| 원문 출처가 도박/베팅 등 신뢰도 낮은 사이트 | 출처명 노출 대신 "전문가들", "한 연구에 따르면" 등으로 일반화 |
| 정치·사회 이슈 | 균형 있게 제시, 필요 시 찬반 투표형 CTA |

### 4-6. 고유명사/인물명 (10장)
- 브랜드·기술명: 원문 표기 유지
- 공직자/공인 실명: 유지 + 영문 병기
- 실존하지 않는 인물(사망 사례 등 민감 소재)은 익명 처리 유지

### 4-7. CTA 구성 (2장)
- 댓글 유도(항상), 공유/저장/태그/팔로우는 콘텐츠 성격에 따라 가변 적용
- 해시태그는 항상 제외

### 4-8. 출력 형식 (15장)
- 후킹 제목(별도) + 본문 + 결론 + CTA를 하나의 코드 블록으로 조립
- "번역입니다" 같은 부연 설명 없이 결과물만 제공

## 6. 기술 아키텍처 제안

| 영역 | 제안 |
|---|---|
| 프론트엔드 | React 기반 SPA, 파일 업로드/드래그앤드롭, 결과 카드형 레이아웃 |
| 백엔드 | 서버리스 함수(또는 경량 API 서버)로 3개 파이프라인(이미지/제목/본문)을 독립 엔드포인트로 분리 |
| 이미지 분석 | 비전 지원 LLM(Claude 등)으로 업로드 이미지의 컨셉·저작권 요소 추출 |
| 이미지 생성 | 별도 이미지 생성 API 연동 (텍스트 없는 이미지 생성 프롬프트로 호출) |
| 텍스트 생성 | LLM API 호출 시 `CLAUDE.md` 전체 규칙을 시스템 프롬프트로 주입 |
| 저장/이력 | 세션 단위로만 유지, 이전 콘텐츠와 연결짓지 않음(1장 원칙) — DB에 영구 저장하지 않거나, 저장하더라도 세션 간 참조 금지 |

## 7. 비기능 요구사항

- **저작권 안전성**: 모든 생성 이미지는 원본을 그대로 사용하지 않고 재생성된 것이어야 하며, 실존 인물·브랜드 로고·IP 캐릭터가 결과물에 나타나지 않아야 한다.
- **일관성**: 동일 규칙(CLAUDE.md) 기반으로 매 요청이 독립적으로 처리되어야 하며, 이전 요청의 톤·소재가 다음 요청에 영향을 주지 않아야 한다.
- **재생성 유연성**: 이미지/제목/본문 각각을 개별적으로 재생성할 수 있어야 한다 (전체를 다시 만들 필요 없이).
- **가독성**: 본문 결과물은 코드 블록(복사 가능한 텍스트 상자) 형태로 제공되어야 한다.

## 8. 개발 단계 제안

| 단계 | 내용 |
|---|---|
| 1단계 | 본문 각색 파이프라인 구현 (텍스트 입력 → 규칙 기반 번역·각색 → 코드 블록 출력) |
| 2단계 | 제목 추천 파이프라인 구현 (원문 제목/이미지 → 후킹 제목 3안) |
| 3단계 | 이미지 재생성 파이프라인 연동 (비전 분석 → 프롬프트 구성 → 이미지 생성 API 호출) |
| 4단계 | 프론트엔드 UI 통합, 개별 재생성 기능 구현 |
| 5단계 | 실제 예시들로 QA (지금까지 검토한 예시들을 회귀 테스트 케이스로 활용) |

## 9. 리스크 및 고려사항

- **이미지 생성 API 저작권 정책**: 사용할 이미지 생성 API 자체의 저작권/콘텐츠 정책도 함께 확인 필요 (예: 실존 인물 생성 제한 여부)
- **문체 일관성 검증**: ~습니다체/~죠/~나요 혼용 비율을 자동으로 점검하는 후처리 체크(19장 체크리스트 기반)를 추가하면 품질이 안정적
- **민감 콘텐츠 필터링**: 의학/사망/극단적 다이어트 등 민감 소재는 자동 필터가 과도하게 순화하거나 반대로 놓치지 않도록 별도 테스트 케이스 확보 필요
- **API 비용**: 이미지 생성 + LLM 호출이 요청마다 발생하므로 재생성 남용 시 비용 관리 고려
